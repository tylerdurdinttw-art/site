# YnaziCotTV

Админ-панель для серверов Rust: мониторинг игроков, античит, репорты.
Первый этап — страница «Игроки» + Oxide-плагин `YnaziCotTvBridge`, поставляющий данные с игровых серверов.

## Регистрация и вход

Панель закрыта целиком: без сессии страницы уводят на `/login`, а `/api/*` отвечает
`401 unauthorized`. Открыты только `/login`, `/verify`, `/api/auth/*` и эндпоинты плагина
(`/api/ingest/*`, `/api/pair`) — у последних своя авторизация по HMAC.

**Регистрация** — логин, почта и пароль. Учётка создаётся сразу, но войти по ней нельзя,
пока не открыта ссылка из письма. **Первый зарегистрировавшийся становится владельцем**
(`role = "owner"`), остальные — `moderator`. После первой учётки регистрацию можно закрыть
переменной `SIGNUP_OPEN="false"`.

**Письмо** уходит через обычный SMTP (`nodemailer`). Пока `SMTP_HOST` пуст, письма не
отправляются: текст письма печатается в лог сервера, а ссылка показывается прямо в интерфейсе —
так поднимается первая учётка на свежем сервере, где почта ещё не настроена. Ссылка живёт 24 часа
и гасится после первого использования.

**«Запомнить меня»** — галочка на форме входа. Она делает две вещи:

| | без галочки | с галочкой |
|---|---|---|
| кука сессии `qp_session` | сеансовая, умирает с браузером | 30 дней |
| строка в `sessions` | 12 часов | 30 дней |
| кука `qp_login` | удаляется | логин на год, форма входа подставляет его сама |

Пароль в куках не хранится — положить его туда безопасно нельзя. Запоминается логин
и сама сессия, этого достаточно, чтобы не вводить данные заново.

### Как устроены сессии

| Слой | Что проверяет |
|---|---|
| `middleware.ts` (edge) | подпись куки HMAC-ключом `AUTH_SECRET` и срок в самой куке |
| `requireUser()` в страницах | живую строку в таблице `sessions` |
| `requireApiUser()` в `/api/*` | то же самое, поэтому «Выйти» действительно отзывает доступ |

Кука выглядит как `<sid>.<secret>.<срок>.<подпись>`. Подделать её без `AUTH_SECRET` нельзя,
а в базе от `secret` лежит только `sha256` — по дампу базы войти не получится. Пароли хранятся
scrypt-хэшем (`node:crypto`, N=16384), отдельных зависимостей вроде bcrypt не нужно.

Смена `AUTH_SECRET` разлогинивает всех сразу.

## Вход в панель и онбординг

Панель обслуживает один проект — строка `Project` в базе всегда одна (`id = "default"`).
От её состояния зависит, куда попадёт вошедший пользователь с `/`:

| Состояние                | Куда ведёт |
| ------------------------ | ---------- |
| проекта нет              | `/welcome` — название, ссылка `quickpanel.com/<slug>` и логотип |
| проект есть, онбординг не закрыт | `/start` — «Начало работы» |
| онбординг закрыт         | `/players` |

«Начало работы» — цепочка из четырёх шагов: следующий открывается только после предыдущего,
закрытые шаги видны, но приглушены и без кнопок. Пока цепочка не пройдена, остальные разделы
сайдбара возвращают на `/start`.

1. **Подключите ваш сервер** — окно с плагином и одноразовым кодом. Механика прежняя:
   `POST /api/pair/code` выдаёт код, плагин обменивает его на ключи командой
   `ynazicottv.setup <код>`. Шаг закрывается, когда в базе появился сервер.
2. **Пригласите команду** — модераторы проекта. Шаг закрывается с первым приглашением.
3. **Выдайте права** — набор из `lib/permissions.ts` для каждого модератора. Новый сотрудник
   создаётся без прав, поэтому шаг требует явного действия.
4. **Начните работу** — закрывает онбординг (`Project.onboardingDone`) и открывает `/players`.

Шаги считаются по фактическому состоянию проекта, а не по счётчику: если убрать всех
модераторов, третий и следующие шаги снова закроются. Пройденный максимум пишется
в `Project.onboardingStep` — по нему видно, где пользователь остановился.

## Установка

Нужны Node.js 18.18+ и PostgreSQL 14+.

```bash
npm install
```

```bash
cp .env.example .env
```

Заполните `DATABASE_URL` и сгенерируйте ключ подписи кук:

```bash
npm run gen:secret
```

Полученную строку впишите в `AUTH_SECRET`. Без него вход работать не будет.

Накатите схему и сид:

```bash
npx prisma db push
```

```bash
npm run db:seed
```

```bash
npm run dev
```

Панель откроется на `http://localhost:3000` и уведёт на `/login`. Зарегистрируйте первую
учётку — она станет владельцем. SMTP локально не нужен: ссылку подтверждения панель покажет
прямо на экране и продублирует в лог.

Сид нужен только для страницы «Игроки»: он заводит два сервера и десять игроков. На главной эти
серверы будут показаны как оффлайн (heartbeat от них не приходит). Чтобы увидеть пустое состояние
со сценарием подключения, поднимайте базу без сида.

## Переменные окружения

| Переменная | Обязательна | Назначение |
|---|---|---|
| `DATABASE_URL` | да | строка подключения PostgreSQL |
| `AUTH_SECRET` | да | ключ подписи кук сессий, от 32 символов; смена разлогинивает всех |
| `APP_URL` | да | внешний адрес панели: из него собираются ссылки в письмах, а `https://` включает флаг `Secure` у куки |
| `SMTP_HOST` | нет | хост SMTP; пусто — письма не уходят, ссылка печатается в лог и показывается в интерфейсе |
| `SMTP_PORT` | нет | порт SMTP, по умолчанию 587 |
| `SMTP_SECURE` | нет | `true` для SMTPS; пусто — определяется по порту (465 = true) |
| `SMTP_USER` / `SMTP_PASS` | нет | логин и пароль почтового ящика |
| `MAIL_FROM` | нет | адрес в поле «От кого» |
| `SIGNUP_OPEN` | нет | `false` закрывает регистрацию; первую учётку заводят всегда |
| `GEOLITE2_CITY_DB` | нет | путь к `GeoLite2-City.mmdb`; без неё город и страна берутся из запасного источника |
| `GEOLITE2_ASN_DB` | нет | путь к `GeoLite2-ASN.mmdb`; без неё провайдер берётся из запасного источника |
| `IP_LOOKUP_FALLBACK` | нет | `off` запрещает ходить в ip-api.com, когда локальных баз нет; по умолчанию `on` |
| `IP_INFO_TTL_DAYS` | нет | срок жизни кеша `ip_info`, по умолчанию 30 |
| `VPN_ASN_KEYWORDS` | нет | дополнительные подстроки для признака VPN, через запятую |
| `STEAM_API_KEY` | нет | ключ Steam Web API; **без него VAC/EAC и часы неизвестны** — карточка так и пишет, значков блокировок не будет. Ключ, заданный в разделе «Разработка», перекрывает эту переменную |
| `STEAM_CACHE_TTL_HOURS` | нет | срок жизни кеша `steam_profiles`, по умолчанию 12 |
| `DISCORD_TIMEOUT_MS` | нет | сколько ждать ответа Discord при отправке вебхука, по умолчанию 10000 |
| `INGEST_MAX_SKEW_SEC` | нет | допустимый возраст запроса по `X-Timestamp`, по умолчанию 60 |
| `INGEST_RATE_LIMIT_PER_MIN` | нет | лимит ingest-запросов на сервер, по умолчанию 60 |
| `RUSTMAPS_API_KEY` | нет | ключ rustmaps.com для карты по seed; без него используется рельеф от плагина |

Базы GeoLite2 скачиваются вручную с maxmind.com (бесплатный аккаунт) и кладутся в `./geoip`.
Внешние гео-API не используются: обогащение идёт только по локальным `.mmdb`.

## Как подключить сервер

Два шага, править конфиг руками не нужно.

1. Скачайте `plugin/YnaziCotTvBridge.cs` (или кнопкой «Скачать плагин» на главной)
   и положите в `oxide/plugins` игрового сервера — Oxide подхватит его сам.

2. На главной нажмите «Подключить сервер», скопируйте команду и выполните её
   в консоли сервера или через RCON:

```bash
ynazicottv.setup ABCD-2345
```

Плагин обменяет код на `serverId`, `serverKey` и `serverSecret`, сам запишет их
в `oxide/config/YnaziCotTvBridge.json` и сразу начнёт слать heartbeat. Панель увидит
сервер в течение 30 секунд — экран подключения сам переключится на «Сервер подключён».

Адрес панели в команде не передаётся: плагин берёт его из своего конфига, поле `ApiUrl`.
По умолчанию там `http://localhost:3000`. Если панель развёрнута по другому адресу — либо
поправьте `ApiUrl` один раз, либо передайте адрес первым аргументом:

```bash
ynazicottv.setup https://панель.example ABCD-2345
```

Проверить состояние можно из консоли командой `ynazicottv.status` или в игре — `/panel status`
(нужен пермишен `ynazicottv.admin`).

Про коды:

- код одноразовый и живёт 15 минут, после обмена сгорает;
- если код просрочен, нажмите «Новый код» — старый станет бесполезен;
- `POST /api/pair` — единственный эндпоинт без HMAC-подписи: подписывать ещё нечем,
  секрет выдаётся именно им. Роль пароля играет сам код.

Повторный `ynazicottv.setup` с обычным кодом заводит **новую** запись сервера, а не обновляет
старую — так две машины с одинаковым hostname не сольются в одну.

### Меню сервера

Шестерёнка на карточке сервера (`/servers`) открывает три действия:

- **Переподключить** — `POST /api/servers/{id}/reconnect` выдаёт код, **привязанный к этому
  серверу**: в `pairing_codes.serverId` он проставляется ещё до обмена. Плагин выполняет
  ту же команду `ynazicottv.setup <код>`, но `POST /api/pair` видит привязку и перевыдаёт
  ключи существующей записи вместо создания новой. Игроки, баны и история остаются на месте.
- **Скачать плагин** — `GET /api/plugin/download`.
- **Удалить** — `DELETE /api/servers/{id}` после подтверждения. Каскады схемы уносят сессии,
  события, репорты, баны, проверки и очередь команд этого сервера; сами игроки остаются,
  у них просто обнуляется привязка. Диалог об этом честно предупреждает и предлагает
  переподключение как безопасную альтернативу.

## Ручная привязка без кода

Обычно не нужна — остаётся на случай, когда сервер не может достучаться до панели по HTTP
или ключи выдаются заранее.

1. В таблице `servers` создайте запись сервера — `id`, `name`, `serverKey`, `serverSecret`.
   Сид уже создаёт две записи для разработки:

   | serverId | serverKey | serverSecret |
   |---|---|---|
   | `rust-1` | `dev-key-rust-1` | `dev-secret-rust-1` |
   | `rust-2` | `dev-key-rust-2` | `dev-secret-rust-2` |

   Для боевого сервера сгенерируйте свои значения, например `openssl rand -hex 32`.

2. Положите `plugin/YnaziCotTvBridge.cs` в `oxide/plugins` игрового сервера
   (или скачайте его кнопкой «Скачать плагин» на главной).
   Oxide скомпилирует плагин и создаст `oxide/config/YnaziCotTvBridge.json`.

3. Заполните конфиг:

```json
{
  "ApiUrl": "http://localhost:3000",
  "ServerId": "rust-1",
  "ServerKey": "dev-key-rust-1",
  "ServerSecret": "dev-secret-rust-1",
  "HeartbeatIntervalSec": 30,
  "CommandPollIntervalSec": 10,
  "AfkThresholdSec": 300,
  "TrackChat": true,
  "TrackSigns": true,
  "AntiCheat": {
    "Enabled": true,
    "ReportViolations": true,
    "HeadshotRatioThreshold": 0.75,
    "MinShotsForRatio": 40,
    "MaxShotsPerSecond": 12,
    "MaxKillDistance": 350
  }
}
```

4. Перезагрузите плагин: `oxide.reload YnaziCotTvBridge`.

5. Выдайте себе доступ к чат-командам:

```
oxide.grant user <SteamID> ynazicottv.admin
```

В игре — `/panel status`: покажет адрес панели, размер очереди и когда был последний успешный запрос.

## Протокол ingest

Все запросы плагина подписываются:

| Заголовок | Значение |
|---|---|
| `X-Server-Key` | `ServerKey` из конфига, ищется в `servers.serverKey` |
| `X-Timestamp` | unix-время в секундах; запрос старше 60 секунд отклоняется |
| `X-Signature` | HMAC-SHA256 сырого тела запроса на `ServerSecret`, hex в нижнем регистре |

Подпись считается от **сырого** тела, поэтому панель читает `req.text()` и не пересобирает JSON.
Для `GET /api/ingest/commands` подписывается пустая строка.
Лимит — 60 запросов в минуту на `ServerKey`, при превышении приходит `429` с `Retry-After`.

## Что работает на этом этапе

- В сайдбаре остались только разделы со страницами: «Игроки», «Чат», «Репорты», «Проверки»,
  «Карта», «Блокировки», «Серверы», «Настройки», «Общее» и «Сотрудники». Внизу — аккаунт
  и кнопка выхода.
  Пунктов-заглушек больше нет: «Рисунки», «Оповещения», «Спальники», «Муты», «Статистика»,
  «Журнал аудита» и «Интеграции» убраны, нижняя панель с иконками — тоже.
- Поиск в сайдбаре рабочий: пока поле пустое, меню обычное, с первым символом оно сменяется
  выдачей. Ищет по названиям разделов и по игрокам — нику и SteamID (список берётся из
  `/api/players` один раз за сеанс). Игрок из выдачи ведёт на `/players?player=<steamId>`,
  и карточка открывается сама.
- `/chat` — лента сообщений и панель фильтров. Пока ни один сервер не прислал heartbeat, вместо
  сообщений показывается предупреждение «Плагин не подключён» с кнопкой скачивания. Панель фильтров
  рабочая: ключевые слова хранятся в таблице `chat_keywords`, цвет пометки — в `panel_settings`
  под ключом `chat.highlightColor`. Сообщения, содержащие ключевое слово, красятся этим цветом.
  Кнопка-корзина в шапке чистит список в два клика: первый взводит подтверждение, второй удаляет.
  Отправка сообщений отключена — авторизации в панели нет.
- `/` — обзор: пять карточек и список серверов. Пока серверов нет, список показывает пустое
  состояние с круглой кнопкой «+»: она раскрывает экран подключения с одноразовым кодом и
  готовой командой для консоли. Панель сама опрашивает статус кода и переключается на
  «Сервер подключён», как только плагин обменяет код на ключи. Рядом кнопка «Скачать плагин» —
  `GET /api/plugin/download` отдаёт `plugin/YnaziCotTvBridge.cs` как вложение.
- `/map` — реальная карта сервера с живыми позициями игроков.
- `/players` — список игроков; строка кликабельна и открывает карточку игрока (см. ниже).
- Рабочие элементы: «Обновить статистику», «Включить автообновление» (15 сек),
  сортировка по колонкам «Игрок», «Тип», «Репорты», закрытие тостов.
- Кнопка «Фильтры» в шапке раздела раскрывает панель с вариантами и фильтрует список на месте:
  на «Игроках» — статус и сервер, в «Репортах» — состояние (на проверке, забаненные, без разбора)
  и сервер, в «Чате» — канал и сервер. Когда фильтр отличается от «все», кнопка подсвечена.
- Авторизации нет: сотрудники в панели описывают приглашения, а не живые учётки.
- Тосты приходят по SSE; при недоступности SSE клиент сам переходит на поллинг раз в 10 секунд.

Стат-карточка «Онлайн» считает игроков на сервере — `online + sleeping`,
как и подпись фильтра «На сервере (онлайн + спят)»; «Оффлайн» — все остальные.
`total` считается по всем известным SteamID, история не удаляется.

## Карточка игрока

Клик по строке в списке открывает окно по центру экрана — `GET /api/players/{steamId}`.
Слева двенадцать вкладок, но сделана только «Обзор»: остальные рендерятся как `<div>`
и ничего не переключают, как пункты-заглушки в сайдбаре. Кнопки «сообщение», «блокировка»
и «ключ» в шапке — тоже заглушки, работают только «Проверка» и закрытие.

Что показывает «Обзор»:

| Группа | Поле | Откуда |
|---|---|---|
| Об игроке | Режим игры | размер команды из heartbeat: 1 — соло, 2 — дуо, 3 — трио, 4 — сквад, 5+ — клан |
| Об игроке | Язык | `lang.GetLanguage` на игровом сервере |
| Играл на | Сервер | сервер, где игрок был замечен последним |
| Играл на | Steam ID | `players.steamId` |
| Играл на | Впервые замечен | `players.createdAt` — первое появление на серверах проекта |
| Играл на | Наигранно на проекте | сумма `player_sessions.durationSec` плюс текущая незакрытая сессия |
| Сеть | IP адрес | последний известный IP из heartbeat |
| Сеть | Страна, город | локальная база GeoLite2-City |
| Сеть | Провайдер | локальная база GeoLite2-ASN |
| Сеть | VPN | вывод по названию организации ASN, см. `src/lib/vpn.ts` |
| Steam | Часы в Rust | `IPlayerService/GetOwnedGames` по appid 252490 |
| Steam | VAC | `ISteamUser/GetPlayerBans`, поле `VACBanned` + дней с бана |
| Steam | EAC | там же, `NumberOfGameBans` + дней с бана |

**IP кликабелен.** По клику раскрывается окошко (`IpLink` + `GET /api/ip?address=…`):
провайдер, город, страна и список тех, кто играет с этого же адреса. Соседи ищутся дважды —
по текущему IP игроков и по истории `player_sessions`, поэтому в списке видно и тех, кто
заходил с адреса раньше (такие помечены словом «раньше»). Гео берётся из локальных баз
MaxMind тем же `lookupIp`, что и при ingest, — наружу панель не ходит.

Про источники этих полей:

- Город, страна и провайдер берутся из **локальных** баз MaxMind — внешние гео-сервисы
  вроде 2ip.ru не вызываются, IP игроков наружу не уходят.
- VPN определяется по названию организации ASN: дата-центры, хостинги и известные VPN-сервисы
  отличаются от домашних операторов названием. Метод грубый, поэтому это признак, а не факт;
  список слов лежит в `src/lib/vpn.ts` и расширяется через `VPN_ASN_KEYWORDS`.
- Часы и блокировки читаются через Steam Web API и кешируются в `steam_profiles`
  на `STEAM_CACHE_TTL_HOURS`. Без `STEAM_API_KEY` эти три поля показывают прочерк.
- Отдельного признака EAC у Steam нет: бан EAC приходит как игровой бан аккаунта
  (`NumberOfGameBans`). Дней с бана Steam отдаёт одно число сразу на VAC и игровой бан.

## Баны

Раздел `/bans` работает с таблицей `bans`, которую наполняет плагин: он ловит `OnUserBanned`
и шлёт событие `player_banned`. Панель сама записей не создаёт даже когда банит из проверки —
источник правды один, поэтому дублей не бывает.

Наверху два счётчика (всего и активных, считаются по всей таблице, а не по фильтру),
ниже — вкладки, фильтры, массовые действия и таблица.

**Вкладки и фильтры.** «Активные баны» и «История банов» — это шорткат для селекта «Статус»:
вкладка выставляет `active` или `all`, поэтому таблица и селект не расходятся. Поиск по нику
и причине регистронезависимый (`mode: 'insensitive'`), по SteamID — по вхождению. Ввод
дебаунсится на 300 мс, а гонка ответов гасится счётчиком запросов: медленный ответ не
перетирает свежий.

**Колонка «Админ»** заполняется только для банов, выданных из панели, — там стоит «Панель».
Автора бана, сделанного в игре, узнать неоткуда: `OnUserBanned` его не передаёт, и в панели
нет авторизации, так что подписывать баны конкретным модератором пока нечем. Панель узнаёт
себя по недавно завершённой проверке с исходом «бан» (`resolveBanAdmin`, окно 5 минут);
сопартийцы при бане тимы связываются с проверкой лидера по совпадающей причине. Всё
остальное показывается прочерком.

**Разбан.** Кнопка `Unban` в строке и «Разбанить всех игроков» помечают записи снятыми
и ставят плагину команду `unban` — тот выполняет консольную `unban <steamid>`. Без команды игрок остался бы
в бан-листе игрового сервера, а панель показывала бы его разбаненным.

**Очистка истории** удаляет записи только из панели и на игровой сервер не влияет —
забаненные останутся забаненными. Оба массовых действия необратимы, поэтому каждое
подтверждается диалогом, где написано, что именно произойдёт.

## Репорты из игры

Кроме нативного F7-репорта (`OnPlayerReported`) плагин даёт своё меню — чат-команда `/report`
(имя настраивается, `Reports.Command` в конфиге). Открывается экран «FIND PLAYER» с сеткой 6×3:
у каждого игрока на фоне карточки его аватарка из Steam, снизу тёмная плашка с ником
и SteamID под ним. Справа полоса прокрутки со стрелками — по 18 игроков на страницу.
Поле «Enter nickname/steamid» ищет по нику и по SteamID; поиск заглядывает и к спящим,
а по полному SteamID пожаловаться можно и на того, кто уже вышел с сервера.

Клик по карточке открывает вторую страницу: причина из списка (`Reports.Reasons`,
по умолчанию Cheating / Insults / Spam / Bug abuse / Other), необязательное сообщение
и кнопка отправки. Меню закрывается кликом мимо окна — Esc до CUI не доходит.

**Пауза между репортами** — `Reports.CooldownSec`, по умолчанию 600 секунд: один игрок может
пожаловаться на одного и того же игрока раз в 10 минут. Ограничение считается по паре
«жалобщик + цель», на разных игроков репорты идут без задержки. Проверка стоит и при выборе
карточки, и при отправке, поэтому консольной командой её не обойти. Пары живут в памяти
плагина и обнуляются при его перезагрузке.

Отправленный репорт уходит событием `player_reported` — тем же, что и нативный F7-репорт,
поэтому оба ложатся в `reports` и увеличивают `players.reportsCount`. Причина попадает
и в `subject`, и в `type`.

**Аватарки** берутся из публичного XML профиля Steam (`steamcommunity.com/profiles/{id}?xml=1`),
ключ Steam API для этого не нужен. Ответ кешируется на всю сессию сервера, один и тот же
профиль второй раз не запрашивается, а клиент грузит саму картинку по ссылке сам.
Пока ссылка не пришла (или `Reports.LoadAvatars: false`), карточка показывает серый квадрат
с «?» — как в макете. Меню перерисовывается один раз через 0.75 секунды после того,
как поток ответов от Steam утих, иначе перерисовка сбивала бы ввод в поиске.

### Раздел «Репорты»

`/reports` устроен как «Игроки»: та же шапка с поиском и та же таблица, только строки —
игроки, на которых жаловались. Одна строка — один игрок, а не одна жалоба: число репортов,
причина и автор последней, время и сервер. Рядом с ником бейджи «На проверке» и «Забанен»,
если это про него. Клик по строке открывает ту же карточку игрока, что и в «Игроках».

Список считается в `src/lib/reports.ts` и слушается настроек раздела: «Удалять репорты
спустя время» отсекает старые жалобы, «Игнорировать репорты после проверки» убирает из выдачи
тех, кого недавно проверяли. Поиск идёт по нику, SteamID, причине и автору жалобы.

## Настройки

`/settings` — три вкладки: «Репорты», «Проверки» и «Баны». Значения лежат одной строкой JSON
в `panel_settings` под ключом `moderation`, читаются и пишутся через `GET`/`PATCH /api/settings`.
Браузер шлёт только изменённую секцию, сервер докладывает остальное из текущих настроек
и прогоняет всё через `normalizeSettings` — битое значение не ломает раздел, а заменяется
умолчанием. Кнопки «Сохранить» нет: переключатель уходит на сервер сразу.

Настройки не декоративные — вот что они меняют:

| Настройка | Где срабатывает |
|---|---|
| Удалять репорты после блокировки | ingest события `player_banned` |
| Удалять репорты после проверки | `POST /api/checks/{id}/finish` |
| Удалять репорты спустя время | выборка `/api/reports` |
| Игнорировать репорты после проверки | выборка `/api/reports` |
| Минимальное кол-во жалоб для начала проверки | `POST /api/players/{steamId}/check` |
| Оповещение о начале проверки в чате | команда `check_announce` при вызове |
| Оповещение о завершении проверки | команда `check_announce` при исходе `passed` |
| Вердикты проверок | список причин в окне «Итог проверки» |

«Удалить все репорты» на вкладке «Репорты» чистит таблицу `reports` и обнуляет
`players.reportsCount`; действие необратимо, поэтому спрашивает подтверждение.

Причины блокировок, причины бана команды и вердикты проверок — поля-чипсы: значение
добавляется по Enter, убирается крестиком. Дубли схлопываются, до 24 значений в списке.

Настройки «Ограничение на количество блокировок», «Отправлять оповещение о бане в чат»
и «Оповещать игроков отправивших репорт» пока только хранятся: банов панель не выдаёт сама,
а рассылка жалобщикам требует адресных сообщений, которых в плагине ещё нет.

## Раздел «Общее»

`/general` — название, ссылка и логотип проекта плюс его номер. Поля сохраняются по уходу
фокуса: `PATCH /api/project` с `name` или `slug`, логотип — `POST /api/project/logo`
той же проверкой типа и размера, что и при создании проекта. Занятая ссылка возвращает 409.

Номер проекта считается из даты создания (`projectPublicId`), поэтому переименование
и смена ссылки его не меняют. Отдельного поля в базе под него нет.

## Раздел «Интеграции»

`/integrations` — вебхуки Discord. Каналов два, и вебхук у каждого свой: их обычно разводят
по разным каналам сервера.

| Канал | Что уходит | Откуда шлётся |
|---|---|---|
| Бан-лист | новая блокировка и снятие блокировки | ingest события `player_banned` и `player_unbanned` |
| Репорты | каждая жалоба игрока | ingest событие `player_reported` |

Настройки лежат одной строкой JSON в `panel_settings` под ключом `integrations`
(`{ discord: { bans: { webhookUrl, enabled }, reports: { … } } }`) и правятся через
`GET`/`PATCH /api/integrations`; кнопка «Отправить тест» — `POST /api/integrations/test`
с полем `channel`. Старая запись с одним вебхуком на всё (`{ webhookUrl, reports: true }`)
читается по-прежнему: адрес из неё переносится в канал «Репорты».

Адрес проверяется регулярным выражением по домену Discord и на сервере, и в браузере:
поле, куда можно вписать произвольный хост, — это готовый инструмент для запросов
с нашего сервера куда угодно. Пустая строка — осознанная отвязка. Ошибки доставки
только пишутся в лог: недоступный канал не должен ломать приём события с игрового сервера.

Причина неудачи разбирается и пишется по-русски — по ней сразу видно, где чинить:

| Что показывает панель | Что это значит |
|---|---|
| «Discord не ответил за N с» | с сервера панели не открывается discord.com: блокировка провайдера или фаервол. Вебхук исправен, менять его бесполезно; срок ожидания — `DISCORD_TIMEOUT_MS` |
| «Не удалось разрешить discord.com» | на сервере панели не работает DNS |
| «Соединение сброшено» | запрос режет фаервол или провайдер |
| «Discord ответил 401/403/404: такого вебхука уже нет» | вебхук удалён или перевыпущен в настройках канала — создайте заново и вставьте новый адрес |
| «Discord придержал сообщение (429)» | слишком часто; Discord вернёт приём сам |

## Раздел «Разработка»

`/dev` — служебный раздел разработчиков сайта. В сайдбаре он дописывается в группу «Проект»,
но только тем логинам, что перечислены в `DEVELOPER_LOGINS` (`src/lib/devShared.ts`);
всем остальным и страница, и её эндпоинты отвечают 404. Списка нет в базе намеренно:
иначе владелец проекта смог бы выписать доступ себе через свою же панель. Права сотрудников
здесь ни при чём, и срок доступа проекта тоже не проверяется — раздел открыт даже тогда,
когда он вышел, иначе продлить его самому себе было бы неоткуда.

| Что можно | Как это работает |
|---|---|
| Вставить ключ Steam Web API | `GET`/`PUT`/`POST /api/dev/steam`; значение ложится в `app_settings` под ключом `steam_api_key` и перекрывает `STEAM_API_KEY`. Кнопка «Проверить» дёргает Steam по публичному профилю |
| Продлить доступ по нику | `POST /api/dev/access` — то же, что `npm run access -- grant`: месяцы прибавляются к остатку. Ник — логин или почта; продлевается проект, где человек владелец |
| Закрыть доступ | тот же эндпоинт с `action: "revoke"` — панель проекта начнёт показывать «Продление» |
| Посмотреть все проекты | `GET /api/dev/access`: владелец, число серверов и срок по каждому проекту |

Права сотрудника разработчика не ограничивают: `requirePermission` пропускает его всегда,
как владельца проекта. Иначе логин из `DEVELOPER_LOGINS`, приглашённый в чужой проект
модератором с пустым набором прав, не смог бы открыть ни чат, ни интеграции, ни настройки
в том самом проекте, который приехал чинить.

Сам ключ Steam наружу не отдаётся никогда — только признак «задан» и последние четыре
символа. Ключ из `app_settings` читается с коротким кешем в памяти процесса (10 секунд),
чтобы правка вступала в силу сразу, но каждый запрос к Steam не ходил в базу за строкой.

## Вызов на проверку

Кнопка «Проверка» в шапке карточки делает `POST /api/players/{steamId}/check`. Панель заводит
запись в `player_checks` и кладёт в `server_commands` команду `check`. Плагин забирает её при
следующем опросе очереди, **сразу поднимает баннер на весь экран** (поэтому проверка стартует
с `bannerVisible = true`, отдельно нажимать «Показать баннер» не нужно) и дублирует вызов в чат:

```
Вас вызвали на проверку. Напишите в чат: /ds ваш_дискорд
```

Ответ игрока — чат-команда `/ds <дискорд>`, она доступна без пермишенов. Плагин шлёт
событие `discord_linked`, панель сохраняет значение в `players.discord`.

Панель отказывается ставить команду с понятной ошибкой, если игрок оффлайн, не привязан
к серверу, сервер не присылал heartbeat дольше двух минут или на игрока пожаловались реже,
чем требует настройка «Минимальное кол-во жалоб для начала проверки» — иначе предупреждение
никто не увидит. Повторный клик по «Проверке» не заводит вторую проверку, а открывает текущую.

### Страница проверки

Вызов на проверку уводит на `/checks/{id}` — отдельную страницу этой проверки (`CheckRoom`).
Слева лента и поле ввода, справа карточка игрока: состояние, статистика, сеть и данные Steam —
то же, что показывает вкладка «Обзор» модального окна. В шапке — хлебные крошки
«Проверки › #номер»; номер считается из `id` (`checkNumber`), чтобы в заголовок не лез cuid.
Страница опрашивает `GET /api/checks/{id}` раз в 3 секунды, карточку игрока — раз в 15.

Что на ней есть:

- **лента** — вехи проверки и переписка одним потоком: начало проверки, сообщения игрока
  и панели, завершение с исходом и причиной;
- **Показать табличку** / **Убрать табличку** — `POST /api/checks/{id}/banner` с `{ show }`.
  Команды `check_banner` / `check_banner_hide`. Баннер поднимается и сам, вместе с вызовом;
  кнопка нужна, чтобы вернуть его после «Убрать» или после перезагрузки плагина;
- **Завершить** — окно с исходом: `passed` («Игрок прошел проверку»), `ban` (вердикт берётся
  из списка в настройках, его можно дописать руками), `team_ban` («Игра с читером», банится
  вся команда из `RelationshipManager`) и `cancelled` (причина из готовых или своя);
- **поле ввода** — `POST /api/checks/{id}/message`, команда `check_pm`. Плагин отвечает
  `SendReply` конкретному игроку, сообщение видит только он.

Сообщения игрока попадают в ленту из обычной пачки `chat_message`: `recordPlayerMessages`
раскладывает их по активным проверкам (`src/lib/checks.ts`).

Задержку переписки убирают с двух сторон: плагин у игроков под проверкой сливает буфер чата
сразу и тут же разбирает очередь (`FlushChatNow`, иначе запрос ждал бы тика `ProcessQueue`
до секунды), а страница слушает SSE `/api/events/stream` и перечитывает переписку на событии
`chat_message`. Порядок в ingest подобран так, что строки попадают в `check_messages`
**до** `publish`, поэтому на кадре SSE они уже в базе. Поллинг раз в 3 секунды остался
страховкой на случай, если SSE недоступен. Очередь команд при активной проверке
опрашивается раз в 2 секунды вместо обычных десяти.

Раздел «Проверки» остался архивом: он показывает список и переписку, а живая проверка
идёт на своей странице. Открыть её можно из карточки игрока — повторный вызов на проверку
возвращает ту же самую и уводит на неё.

### Баннер

Прозрачный CUI-слой на весь экран поверх игры, курсор не перехватывается. Крупный красный
заголовок по центру, под ним три строки про Discord и блокировку и строка с командой `/ds`.
Читаемость поверх любого фона даёт чёрная обводка (`CuiOutlineComponent`), поэтому экран
не затемняется. Тексты строк живут в плагине — это оформление; панель шлёт только заголовок
(константа `BANNER_TEXT` в `src/lib/checksShared.ts`), а если он пустой, плагин берёт свой.

### Раздел «Проверки»

`/checks` показывает все проверки из `player_checks`, свежие сверху, до 200 штук.
Селект фильтрует: все / идут сейчас / завершённые / с баном / прошли проверку.
Кнопка «Обновить» перезапрашивает список; автообновления здесь нет — за живыми
проверками следит док, а это архив.

В строке: ник, модератор, сервер, время начала и завершения, бейдж с дискордом
(зелёный, если игрок назвал его командой `/ds`, красный — если нет), число сообщений
в переписке и причина. Клик по строке открывает переписку целиком —
`GET /api/checks/{id}/messages`.

Справа два бейджа, и это разные вещи:

- **верхний — исход этой проверки**: «Идёт», «Забанен», «Бан тимы», «Чист», «Отменена»;
- **нижний — действует ли бан на игрока прямо сейчас**: «Забанен» или «Чист».

Они расходятся законно: игрок мог пройти проверку и получить бан позже за другое,
или быть забаненным по итогу проверки и потом разбаненным. Подписи вынесены
в `title`, чтобы при наведении было видно, что есть что.

Колонка «Модератор» заполняется так же, как «Админ» в банах: пока в панели нет
авторизации, все проверки заводятся из неё и подписываются «Панель».

### Итог проверки

Завершение любым исходом ставит `player_checks.status = finished`, закрывает ввод и шлёт команду
`check_end` — она снимает баннер и возвращает обычный темп опроса. Чат, баннер и статус
проверки пропадают вместе.

Перед этим в очередь уходит итог для игрового чата (`checkResultMessages`):

| Исход | Игроку (`check_result`) | Всему серверу (`check_announce`) |
|---|---|---|
| `ban` | «Вы забанены за …» | «Игрок NAME забанен за …» |
| `team_ban` | «Вы забанены за Игра с читером» | «Команда игрока NAME забанена за Игра с читером» |
| `cancelled` | «Проверка отложена: …» | — |
| `passed` | «Проверка пройдена» | — |

`check_result` ставится **до** команды бана, иначе игрок отключится раньше, чем прочитает
причину. Тот же текст пишется в переписку проверки, чтобы в истории было видно, что ушло.
Записи в `bans` панель сама не делает: бан выполняет плагин, а обратно приходит штатное
событие `player_banned`.

## Как устроена карта

Основной источник — **rustmaps.com**, карта ищется по паре `seed` + размер мира.

1. Плагин присылает `World.Seed` и `World.Size` в каждом heartbeat, панель хранит их в `servers`.
2. При первом заходе на страницу панель дёргает `GET https://api.rustmaps.com/v4/maps/{seed}/{size}`
   с заголовком `X-API-Key`, забирает ссылку на изображение и **скачивает картинку к себе**
   в таблицу `rustmaps_images`. Дальше она отдаётся из базы через `/api/map/image` —
   наружу панель больше не ходит и IP посетителей на rustmaps не утекают.
3. Ключ берётся из `RUSTMAPS_API_KEY` (rustmaps.com → Dashboard → API keys). Без ключа шаг
   пропускается.

Возможные ответы rustmaps обрабатываются отдельно: `409` — карта ещё генерируется, страница
перепроверит сама через 20 секунд; `404` — такого seed у них нет (обычно это кастомная карта);
`401` — ключ не принят. Неудачная попытка запоминается на 10 минут, чтобы не долбить их API
на каждый заход.

### Запасной вариант

Если rustmaps недоступен, ключа нет или карта кастомная, панель показывает рельеф, снятый
самим плагином:

1. Плагин спрашивает `GET /api/ingest/map?seed=…&size=…`. Панель отвечает `needsUpload: false`,
   если карта уже есть на rustmaps — тогда игровой сервер вообще не тратит время на сканирование.
2. Иначе плагин проходит сеткой `MapResolution × MapResolution` (по умолчанию 512) по
   `TerrainMeta.HeightMap`. Проход разбит на порции по 32 строки через `timer.Every(0.05)`,
   чтобы не подвесить сервер на кадр.
3. Высоты нормализуются в один байт на точку и уходят в `POST /api/ingest/map`. Панель хранит
   сетку в `server_maps`, а картинку из неё рисует **браузер** на `canvas`: цвет берётся из
   высоты — ниже нуля вода, дальше песок, трава, камень, снег.

Позиции идут отдельным потоком: раз в `PositionIntervalSec` (по умолчанию 5 секунд) плагин шлёт
`POST /api/ingest/positions` с координатами бодрствующих игроков. Панель держит их **в памяти
процесса**, а не в базе: значения живут секунды и не нужны исторически. Страница опрашивает
`GET /api/map/positions` раз в 3 секунды и рисует каждого игрока кружком с ником внутри;
у AFK обводка жёлтая. Координаты старше 30 секунд считаются протухшими и не отдаются.

Позиции не переживают перезапуск панели — просто появятся снова со следующим тиком плагина.

## Заметки по плагину

- Плагин не поднимает свой HTTP-сервер: только исходящие `webrequest` и поллинг очереди команд.
- Без ключей плагин не ругается ошибкой, а пишет в консоль подсказку про `ynazicottv.setup`
  и просто ничего не отправляет. Таймеры стартуют сразу после успешного подключения,
  перезагружать плагин не нужно.
- Очередь с ретраями: повтор при кодах `0`, `429`, `5xx` с задержкой 2/4/8/16/32 секунды,
  максимум 5 попыток, буфер 500 событий, при переполнении дропаются самые старые с `PrintWarning`.
- Хук `OnPlayerInput` только пишет время в словарь — никаких аллокаций и отправок.
- Плагин никого не банит и не кикает по своей инициативе: он лишь сообщает о нарушениях,
  решение принимает панель или модератор через очередь команд.
- `OnSignUpdated` отправляет SHA-256 изображения; само изображение уходит отдельным
  `multipart/form-data` запросом на `/api/ingest/sign-image`, только если панель ответила
  `{"needImage": true}`. Панель так не отвечает, эндпоинта `/api/ingest/sign-image` нет,
  поэтому изображения не выгружаются.
- Команда очереди `check` ничего не делает с игроком: только баннер и сообщение в чат.
  То же и с `check_banner` / `check_banner_hide` (CUI-слой без курсора), `check_pm`,
  `check_result` (личные сообщения) и `check_announce` (объявление всем). Кик, бан и разбан
  приходят отдельными типами команд: `kick`, `ban`, `ban_team`, `unban`.
- Неизвестный тип команды плагин подтверждает и пишет в консоль предупреждение со своей
  версией: иначе очередь копила бы такие команды вечно. Версия с проверками — `1.1.0`,
  с меню репортов — `1.2.0`, с сообщениями из панели (`say`) — `1.3.0`, с починенным
  разбаном — `1.3.1`; видно в `oxide.plugins` и по `ynazicottv.status`.
- **Реплики из панели работают только с плагином `1.3.0` и новее.** До него типа `say`
  в плагине не было: панель ставила команду в очередь, а на сервере ничего не происходило.
- Меню репортов — единственный CUI-слой плагина с курсором и захватом клавиатуры:
  пока оно открыто, игрок не двигается. Слой снимается при выгрузке плагина
  (`CloseAllReportUi`) и при выходе игрока.
- Пока идёт хотя бы одна проверка, плагин опрашивает очередь раз в 2 секунды вместо
  `CommandPollIntervalSec` и сбрасывает буфер чата сразу после сообщения проверяемого.
  Обычный темп возвращается по команде `check_end`.
- Баннеры снимаются при выгрузке плагина: `Unload` вызывает `CuiHelper.DestroyUi`
  для всех, у кого слой висел. Панель об этом не знает — после перезагрузки плагина
  баннер надо показать заново кнопкой.

| `npm run db:seed` | сид: 2 сервера и 10 игроков |
| `npm run db:studio` | Prisma Studio |
| `npm run access -- list\|grant\|revoke` | сроки доступа проектов; то же самое умеет раздел «Разработка» |
| `npm run user:password` | сменить пароль учётке |

Дев-сервер и прод-сборка лежат в разных папках: `next dev` пишет в `.next-dev`, `next build`
и `next start` — в `.next` (`distDir` в `next.config.mjs` выбирается по `NODE_ENV`). Иначе
запуск `npm run dev` затирал бы сборку, которой прямо сейчас отдаёт страницы `npm start`,
и прод-сервер падал с «Could not find a production build».

## Деплой на хостинг

Панель — это Node-приложение с PostgreSQL. Статический хостинг и обычный «шаред» с php
не подойдут: нужен VPS или сервер, где можно запускать свои процессы.

### Что требуется от сервера

| | Минимум | Комфортно |
|---|---|---|
| CPU | 2 ядра | 2–4 ядра |
| RAM | 2 ГБ | 4 ГБ |
| Диск | 20 ГБ SSD | 40 ГБ SSD |
| ОС | Ubuntu 22.04 / Debian 12 | то же |

Панель держит SSE-соединения и in-memory состояние (rate-limit, шина событий, координаты
игроков), поэтому запускается **одним процессом**. Горизонтальное масштабирование потребует
сначала вынести это состояние в Redis — см. `lib/rateLimit.ts` и `lib/eventBus.ts`.

### Вариант 1 — Docker Compose (проще)

В репозитории есть `Dockerfile` и `docker-compose.yml`: панель и PostgreSQL поднимаются вместе.

```bash
cp .env.example .env
```

Заполните в `.env`: `AUTH_SECRET` (`npm run gen:secret`), `APP_URL` со своим доменом,
`POSTGRES_PASSWORD` и настройки SMTP. `DATABASE_URL` compose подставит сам.

```bash
docker compose up -d --build
```

Первый раз накатите схему:

```bash
docker compose exec app npx prisma db push
```

Панель слушает `127.0.0.1:3000` — наружу её отдаёт nginx (см. ниже).

### nginx и HTTPS

Панель никогда не выставляется в интернет напрямую: перед ней стоит nginx с сертификатом.
Он же держит SSE-соединения, поэтому буферизацию для них надо выключить.

```nginx
server {
    listen 80;
    server_name panel.example.com;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection 'upgrade';
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_cache_bypass $http_upgrade;
        # Поток событий /api/events/stream не должен копиться в буфере nginx
        proxy_buffering off;
        proxy_read_timeout 3600s;
    }
}
```

```bash
sudo certbot --nginx -d panel.example.com
```

После выпуска сертификата **обязательно** поправьте `APP_URL` на `https://…` и перезапустите
приложение: от этого зависит флаг `Secure` у куки сессии и адрес ссылок в письмах.

### Чек-лист перед запуском

- [ ] `AUTH_SECRET` — свой, от 32 символов, не из примера
- [ ] `APP_URL` — реальный домен с `https://`
- [ ] SMTP заполнен и письмо доходит (проверьте регистрацией)
- [ ] порт PostgreSQL наружу закрыт (`ufw allow 22,80,443/tcp`, остальное — deny)
- [ ] после регистрации владельца выставлен `SIGNUP_OPEN="false"`
- [ ] настроен бэкап базы: `pg_dump` по крону
